## 一、先说三条判据

这一版所有结论都按这三条得出，后面每一节都会指出用的是哪一条：

| 判据 | 含义 | 反例（都不算验证） |
|---|---|---|
| **走用户真实路径** | 一次运行走的是用户真实走的那条路，看到用户会看到的结果 | 进程存活、窗口数变化、日志没报错 |
| **回读实际值** | 断言读的是控件的实际几何/颜色，不是"接口返回成功" | `configure()` 没抛异常 |
| **对照法** | 阳性样本必须被拦、阴性样本必须放过 | 检查器"返回通过"（它可能根本没跑） |

端到端冒烟（`tools/e2e_smoke.py`）就是第一条的落地：真实控件 → 真实生成
入口 → 真实事件循环 → **磁盘上真有 mp3 与 srt**。

## 二、上游 API 的变化（这一版最要紧的同步）

**事实**：`edge-tts` 最新是 **7.3.1**（2026-10-13 发布），本项目此前钉在
**7.0.0**（2025-03-16）。中间跨了 7.1 → 7.3，实测确认了四处变化：

| 变化 | 影响 | 处理 |
|---|---|---|
| **自带 SRT 合成**（`edge_tts.srt_composer`） | 7.3.x 起不再依赖外部 `srt` 包 | 从依赖里去掉 `srt`；但**不直接用上游的 `SubMaker`**（见下） |
| `SubMaker.merge_cues()` **被移除** | 旧代码里的自定义 `SubMaker` 抄的是上游老实现，依赖 `srt` 包 | 自己维护一份字幕合成（`subtitles.py`），合并规则可以单独测 |
| `Communicate.__init__` 签名未变 | `rate / volume / pitch / boundary / proxy` 都还在 | 直接透传 |
| `list_voices()` 返回的字段未变 | `Name` 仍是 `Microsoft Server Speech Text to Speech Voice (en-US, AriaNeural)`，`ShortName` 是 `en-US-AriaNeural` | 见下一节 |

**为什么不用上游的 `SubMaker`**：它一个字幕块放一个词，屏幕上会一行一个词
地跳；本项目要的是"最多 5 个词 + 不跨句 + 不跨长停顿"。这是本项目的取舍，
所以自己维护，并写了 `tests/test_srt_parity.py` 保证**输出格式与上游逐块一致**
（格式一旦悄悄变，播放器会什么都不显示，而程序不会报错）。

## 三、修掉的那个"声音对不上"的缺陷

**旧代码**：

```python
voices = sorted([(v['Name'], v['ShortName']) for v in voices], ...)   # 按 Name 排序
voice_combobox = ttk.Combobox(values=[v[1] for v in voices])          # 显示 ShortName
communicate = edge_tts.Communicate(text, voices[voice_index][0])      # 却用 Name
```

`Name` 与 `ShortName` 的排序结果**不一样**（实测 `sorted(names) == sorted(shorts)`
为 `False`），所以下拉框显示的声音和实际合成的声音**不是同一个**。

修法的关键不是"改成传 ShortName"，而是**全程只用一个字段**：
`VoiceCatalog` 里的每一项就是一个 `Voice`，显示用它的 `display`，
调用用它的 `short_name`，中间不再按下标在两个平行列表之间跳。

> **教训（已可复用）**：一个概念有两个"看起来一样"的表示时，选一个当权威，
> 并且所有读取方都走同一个函数。这里差一点就变成"改了显示、没改调用"。

## 四、界面：从 pack 换成 grid

**现象**：窗口明明 880×720，客户区里却只看到编辑区；操作区与底栏
在几何探针里报 `y = -337`——它们**被挤到客户区外面**了。

**根因**：`pack` 下"编辑区 expand"会把高度不足的后果甩给后面的分区。
窗口看起来"只是有点空"，而那两行其实已经跑到窗口外。

**修法**：整个窗口改用 `grid`，每一行显式声明权重：

```python
for row, weight in ((ROW_HINT, 0), (ROW_HEADER, 0), (ROW_SETTINGS, 0),
                    (ROW_EDITOR, 1), (ROW_ACTION, 0), (ROW_STATUS, 0), (ROW_FOOTER, 0)):
    root.rowconfigure(row, weight=weight)
```

**这条缺陷是探针抓出来的，不是看出来的**——屏幕上看不出"少了两个分区"。
所以 `tools/ui_layout_probe.py` 现在把"有没有控件落在客户区之外"写成硬判据。

### 顺带修掉的一个几何陷阱

`_center_window` 里原本有一次 `update_idletasks()`。在**内容建好之前**调它，
Tk 会按"当前需要的尺寸"重算窗口，把刚设的 geometry 顶掉——实测 880×720
变成 517×443。现在屏幕尺寸直接问 Tk，不先布局。

## 五、深浅主题

### 5.1 颜色从系统读，不写死

| 来源 | 用途 | 取值方式 |
|---|---|---|
| `HKCU\...\Themes\Personalize\AppsUseLightTheme` | 深浅模式 | `== 0` 即深色 |
| `HKCU\...\DWM\AccentColor` | 强调色（ABGR） | 低 24 位；为 0 时退到 `AccentPalette` 第 7 组 |
| `GetDpiForSystem()` | 尺寸换算 | 168 DPI ⇒ 4 逻辑像素 = 7 物理像素 |

读不到时安静降级到内置的默认色。**实测这台机器读到 `#2959CC`**（系统强调色），
深色下按规范往白推 0.35 变成 `#7493DE`。

### 5.2 尺寸只换算一次

统一走 `Theme.px(逻辑像素)` 与 `Theme.font(磅值)`。
字体一律用**负的字号**（Tk 语义是"像素高度"），避免 Tk 再按自己的比例缩一次——
否则同一份代码在别的 DPI 下会自己变一套尺寸。

### 5.3 分层靠容器

| 层 | 浅色 | 深色 |
|---|---|---|
| 窗口底 `background` | `#F3F4F6` | `#191919` |
| 卡片 `card` | `#FFFFFF` | `#242424` |
| 输入框 `surface_alt` | `#F7F8FA` | `#2B2B2B` |

**深色下"浮起来"同样靠提亮**，不是压暗。每一层都**点名设色**，不靠
"内层控件改了就跟着变"——复合控件每一层都可能自己画底色。

实测（`ui_layout_probe.py --theme dark` + 抓图取像素）：

```
card bg (36,36,36)   entry (43,43,43)   text area (43,43,43)   accent btn (116,147,222)
```

`#242424` = (36,36,36)、`#2B2B2B` = (43,43,43)，都对得上。

### 5.4 分层规则（v1.1.0 用户定稿：单一底色）

**用户看到的症状**："配色很混乱：部分按钮是独立色块，部分按钮又和背景融在一起
没有边界，部分标题和引导也放在色块内。"

**根因**：第一版按"卡片比窗口亮一档"来分层，于是窗口底、设置卡片、编辑区卡片、
状态卡片、提示条**各是一块颜色**；按钮有三种外观（`neutral` 带灰底、
`ghost` 完全透明、`accent` 强调色），透明的那种自然就"和背景融在一起"。

**定稿规则**（现在只有这三条）：

| 层 | 颜色 | 说明 |
|---|---|---|
| **面板** | 只有一个底色：`background` | `card` **取值与之相同**——不留任何色块 |
| **输入区**（编辑区、四个输入框） | `surface` + `border` 描边 | 比面板亮一档；Windows 上"这里能打字"的惯例 |
| **可点击按钮** | `surface` + `border_strong` 描边 | **同一套逻辑**，`neutral` 与 `ghost` 合并 |
| **主按钮**（生成语音） | `accent` | 按规范只给"推荐的那一个动作"，**保持不变** |

实测回读（`capture_screenshot.py` 取像素）：

```
浅色   面板/提示条/状态区 (243,244,246)   按钮 (255,255,255)   生成语音 (41,89,204)
深色   面板/提示条/状态区 (25,25,25)      按钮 (43,43,43)      生成语音 (116,147,222)
```

**判据写进了探针**（`ui_layout_probe.py`）：

* `card` 必须等于 `background`（出现两种底色就报错）；
* `surface` 不能等于 `background`（否则看不出哪里能打字）；
* `border_strong` 不能等于 `background`（否则按钮与背景融为一体）；
* 正文对比度 ≥ 4.5、次要文字 ≥ 3.0；
* **控件树里不能残留系统色**（`SystemButtonFace` / `SystemButtonText`）。

最后一条是这一轮最值钱的判据：它把"漏设了一个控件"变成可查证的失败，
而不是靠人眼看"深色下有那么一块浅的"。

### 5.5 深色主题：两个真 bug（用户实测报回来）

| 症状 | 根因 | 判据 |
|---|---|---|
| **标题栏不变深色** | `window_id_of()` 返回的是 Tk 的**内层**窗口句柄，而 DWM 只认真正的顶层窗口——用错的句柄调 `DwmSetWindowAttribute` 一律返回 `E_HANDLE (0x80070006)`，看起来像"系统不支持"。另外 `argtypes` 没声明，64 位下 HWND 会被截成 32 位 | 加 `GetAncestor(GA_ROOT)` + 声明 `argtypes` 后，同一句调用返回 `S_OK`（实测：raw 句柄 `0x80070006`，root 句柄 `0x00000000`） |
| **语速 % / 音量 % / 音调 Hz 不变深色** | 这三个标签**从未被设色**，回读是 `SystemButtonFace`。`_apply_theme` 靠**手写控件清单**设色，漏了就永远漏 | `_apply_theme` 改成**走一遍控件树**（`_theme_widget_tree`）；探针加"系统色残留"检查 |

> **教训**：`apply_dark_titlebar` 一直返回 `False`，而我把它当成了"这台机器
> 不支持"——**返回值就是判据，我却没看它**。第二次是"手写清单"这个做法本身
> 的问题：清单会漏，遍历不会。

### 5.6 ttk 的处理

* 用 `clam` 作为基底——内置主题里唯一"每个颜色都能改"的一套；
* 下拉列表是 Tk 的 `listbox`，只能通过 `option_add('*TCombobox*Listbox.background')` 上色；
* `tk.Text` / `tk.Entry` 用 tk 自己的选项，不用 ttk；
* 遍历控件树时**跳过 ttk 控件**：它们的颜色由 ttk style 管，用 `configure`
  改不动，硬改只会留下"看起来设了其实没生效"的假象。

### 5.7 「使用提示」窗口的字号

用户先反馈"太小"（升到 12pt），看过之后又反馈"大了"，最后**定稿 10pt**
（与主界面正文同号）。处理方式见第 5.9 节末；要点是**只调提示窗口那一个常量**，
不动共用的 `FONT_SMALL_PT`——主界面那条提示条的宽度是量过的。

### 5.8 按钮：从 Frame 自绘换成 Canvas 圆角自绘

**用户报的症状**："所有按钮外的文字周围和面板之间有淡淡的色差，肉眼能看出来。"

**根因**：按钮当时是 ``tk.Frame`` + ``highlightthickness``，也就是一个**直角**
矩形。像素回读证实：每个按钮都是一块直角白矩形，直角外缘在 175% 缩放下呈现
1~2 像素的灰边——那圈灰边就是"淡淡的色差"。**要圆角就必须自己画**，
而画了圆角，那圈色差同时消失。

现在的实现（`FlatButton(tk.Canvas)`）：

| 点 | 做法 |
|---|---|
| 圆角 | 四段**三次贝塞尔**，控制点用 ``k = 0.5523 × r`` 逼近四分之一圆，每段采样 8 点 |
| 抗锯齿 | 同一条路径画两遍（先描边、后填充），画布底色设成**面板底色**，让圆角之外露出面板色 |
| 尺寸 | 按文字实测宽度 + 内边距算，不留多余空白 |
| 焦点 | `takefocus` + `<Return>` / `<space>`，焦点时用强调色描边 |

半径用规范里的 `radius_button = 8`。

> ⚠️ **形状类的东西必须回读像素验证。** 第一版的贝塞尔端点顺序不一致，
> 画出来是**橄榄形**——而代码读起来"很有道理"。第二版才把它读成一张
> ASCII 像素图确认：圆角处能看到四分之一圆弧的阶梯过渡。

### 5.9 弹窗也必须被主题覆盖（用户报"设置窗口不统一"）

**症状**：设置窗口、提示窗口在深色下有一块块浅色。

**根因**：那两个弹窗里的 `FlatButton(...)` **都没传 `theme=self.theme`**
（只传了 `kind`），于是它们永远停在 `SystemButtonFace`。
主窗口的控件树遍历**看不到弹窗**（那是另一棵树），所以一直没被发现。

修法两条：

1. 弹窗里所有按钮显式传 `theme`；
2. **`ui_layout_probe.py` 把弹窗也纳入检查**——打开设置窗口与提示窗口，
   对它们各跑一遍"系统色残留"检查，并加一条**留白判据**：
   `窗口高度 − 内容需要高度 > 40 px` 就报错。

第二条抓出了用户报的另一半问题：设置窗口写死 460 逻辑像素高，
而内容只需要一半，**下面两百多像素全是留白**。现在高度交给 Tk 按内容算
（`_place_toplevel(..., fit=True)`，只给宽度和位置）。

> **同一类缺陷的两个形状**：主窗口是"漏设控件"，弹窗是"根本没进检查范围"。
> 后者更隐蔽——**我的检查器看着一片绿，而它从来没看过那个地方。**

用户先反馈"太小"，升到 12pt 后又反馈"大了"，**定稿 11pt**（主界面正文是 10pt）。

* 只有提示窗口的正文字号单独定义（`FONT_HELP_PT`），**没有动共用的
  `FONT_SMALL_PT`**——那会同时放大主界面的提示条与字数行，而提示条宽度是
  量过的，一放大就会被截断；
* 行距按字号给（`spacing1/3`），不然字号一大就挤在一起；
* 窗口尺寸与位置由 `_place_toplevel()` 统一处理（摆在主窗口中间并夹到屏幕内）。
  原来直接用 `.geometry("600x600")`，实测提示窗口开在屏幕左上角 (0,0)。

## 六、一边改一边修掉的**十一个**缺陷

改的过程中冒出来的。**只有第 1 个是读代码看出来的**，其余都是"让它先跑起来"
或者**用户实测报回来**的——第 7、10、11 个就是后者。

### 6.1 取消生成会炸

`engine.synthesize` 的签名写着 `cancel: Optional[asyncio.Event]`，
而界面侧传的是 `threading.Event`——**两者不通用**。用户在窗口里点取消，
后台线程调 `is_set()` 就会抛 `AttributeError`。

修法：不限定类型，只要求"有个 `is_set()` 能问"（`engine.is_cancelled`），
并在**开始 stream 之前**先查一次取消——否则取消会变成"先连一次网再丢弃"。

**判据**：`test_cancel_mid_stream_keeps_nothing` 断言的是
**输出目录里什么都没留下**，不是"函数抛了异常"。

### 6.2 取消之后终端里多一句没人看得懂的噪音

`Task was destroyed but it is pending`。根因是异步生成器没在事件循环还活着的
时候被 `aclose()`，留到 `loop.close()` 那一刻才回收。
`tools/probe_async_warning.py` 就是为定位它写的——按用例名逐个跑，
把噪音缩到一个用例上。

### 6.3 `_update_counts()` 在控件建好之前被调用

`_build()` 里在建 footer 之前就调了它，于是 `AttributeError`。
修法是把"需要读别的控件"的初始化全部挪到 `_build()` 末尾。

### 6.4 抓图抓错了地方（两次）

| 次数 | 症状 | 根因 |
|---|---|---|
| 1 | 抓到窗口的右半边 + 旁边的资源管理器 | 抓图进程没声明 DPI 感知，`GetWindowRect` 给的是逻辑坐标，而屏幕抓图要物理像素 |
| 2 | 抓到的全是别的窗口 | `SetForegroundWindow` 对"不是前台的进程"会被系统忽略 |

修法：进程声明 Per-Monitor V2 感知 + 按窗口 DPI 换算坐标；
`--method printwindow` 让窗口自己画一遍，不要求它在最前面。

> ⚠️ **注意技术栈差异**：归档里 `PrintWindow(PW_RENDERFULLCONTENT)` 在
> wxPython 上返回乱码，而在 Tk 上可用。所以 `capture_screenshot.py`
> **两条路都留着**，可以互相对照。不要因为一边失败就把另一边也否掉。

### 6.5 打包成 exe 之后，`print()` 会把程序弄崩

**症状**：双击 exe 没反应；命令行里 `GUI-of-Edge-TTS.exe --version` 抛
`AttributeError` / `OSError`。

**根因**：spec 里 `console=False`，冻结之后**没有控制台**，`sys.stdout`
是 `None`——任何一句 `print()` 都炸。而崩溃点可能就在启动路径上。
**这个缺陷只在冻结态出现**，从源码跑永远看不到
（归档 `projects/File-tracker.md` 第五节记过同一个形态）。

修法三步，缺一个都不行：

1. `--version` / `--selftest` / `--smoke` 先 `AttachConsole(ATTACH_PARENT_PROCESS)`
   挂到父进程的控制台（在 cmd/PowerShell/CI 里就有了输出）；
2. 挂不上时（双击运行）把结果写进 `%APPDATA%\…\last-output.txt`，
   并弹一个 **6 秒后自动关闭**的提示框——不静默退出（归档 01 错误六）；
3. **界面路径**里塞一个吞掉一切的 `sys.stdout` 替身
   （`platform_win.silence_missing_streams()`），让任何诊断输出
   **没有能力把程序弄崩**；诊断统一走 `platform_win.report()`。

### 6.6 打包出来的 exe 起不来：Tcl/Tk 的 DLL 没被打进去

**症状**：exe 能跑 `--version`，但一起界面就
`ImportError: DLL load failed while importing _tkinter: 找不到指定的模块`。

**根因**：本机是 conda 环境，`tcl86t.dll` / `tk86t.dll` 在
`Library/bin`，而 PyInstaller 的 tkinter hook 按**标准 cpython 布局**
（`DLLs` / `tcl` 子目录）去找——**分析阶段不报缺，运行时才炸**，
而且报的是一句跟 Tcl 毫无关系的"找不到指定的模块"。

修法：spec 里显式把 DLL 与 `tcl8.6` / `tk8.6` 两个脚本目录带上
（见 `GUI-of-Edge-TTS.spec` 的 `tcl_tk_payload()`），路径从
`sys.base_prefix` 推，**不写死开发机的目录**。

**判据**：打包之后真的把 exe 起起来，看窗口有没有出现
（`tools/capture_screenshot.py --wait-window 60`），以及
`exe --smoke` 能不能在冻结态跑完一次真实生成。

### 6.7 占位提示把用户真实的粘贴挡掉了（**用户实测报回来的**）

**症状**（用户原话）：粘贴内容之后点「生成语音」，"没有正确生成，而是提示
编辑区是空的"；同时"输入提示框文字……用户粘贴内容时它不会自动删除，而是会
混入用户内容"。

两条症状是**同一个根因**：占位提示不是真的占位，它就是普通文本。

```
widget='把要朗读的文字粘贴到这里…\nCtrl+Enter 直接开始生成Hello from the clipboard…'
```

**第一版的写法与它为什么错**：

```python
def _on_modified(self, _event=None):
    if not self.text.edit_modified():   # ← 这面旗子被我自己的代码清了
        return
    ...
    self.text.edit_modified(False)      # ← 而这本身又会触发 <<Modified>>
```

`edit_modified(False)` **会再投递一次 `<<Modified>>`**。两次通知的先后由 Tk
决定，于是"旗子已被清掉"的那一次先到，用户真实的 Ctrl+V 就被守卫挡在门外。
另外插入点默认停在 `1.0`，所以粘贴的内容插到了提示**前面**。

**修法（判据是内容，不是状态位）**：

1. **占位提示用 tag 记住范围**，输入事件里查 `tag_ranges`——不再依赖
   `edit_modified()`；
2. **在 Tk 处理输入之前删掉它**：绑 `<KeyPress>` 与 `<<Paste>>`（这两条都在
   默认绑定**之前**触发）。等处理完再删就得从用户内容里把它挑出来，容易伤到
   用户的东西；
3. 插入点放到占位提示**末尾**，粘贴才会落在提示之后；
4. 输入之后再核对一次内容（菜单粘贴 / 输入法 / 脚本粘贴不走键盘）。

**为什么这不是"再小心一点"能解决的**：`tk.Text` 没有"占位提示"这个概念，
把它当文本插进去就必然要猜"用户动没动"。**判据必须落在内容上。**

**回归判据**：`tools/probe_paste_placeholder.py`（已进 `check_all.py`）。
它用**真剪贴板 + 真实的 `<<Paste>>` 事件**走一遍 Ctrl+V、追加输入、
清空后再粘贴、带坐标粘贴四条路，每一步都回读 `_placeholder_active`、
`get_text()` 与控件里的原文。这个探针**第一版就复现了 7 个问题**。

**顺带**：`_smoke.py` 原本直接写 `app._placeholder_active = False` 来填内容，
**等于绕开了被测代码**——所以它当时全绿而用户一点就坏。现在它改走
`app.set_editor_content()`（"读入文件"按钮的同一条路），并断言
"填完内容之后占位提示不在控件里"。

### 6.8 深色主题没生效：两个真 bug（**用户实测报回来的**）

见第 5.5 节（标题栏句柄错、参数标签从未设色）。这里只记代价：

`apply_dark_titlebar()` 一直返回 `False`，**而我把返回值当成了"这台机器不
支持"，没有查**。它其实每次都返回 `E_HANDLE`——句柄是错的。这是"仪器报出
一个我不喜欢的读数，我就把它解释掉了"。

### 6.9 「使用提示」窗口的字号与位置

用户先反馈"字号太小"（升到 12pt），看过之后又反馈"大了"（定稿 11pt）。
过程见第 5.7 节。

值得记的是**处理方式**：只给提示窗口单独定义字号常量，没有动共用的
`FONT_SMALL_PT`——否则主界面那条量过宽度的提示条会被一起放大并截断。
"用户说某个字太小"不等于"把那个字号常量改大"，要先问**这个常量还被谁用**。

### 6.10 抓图工具自己也有三个坑（"量错了对象"家族）

为了让"F1 之后的提示窗口"能被拍下来，`capture_screenshot.py` 加了 `--keys`。
它自己踩了三次：

| 症状 | 根因 |
|---|---|
| 报了"没有新窗口"，而窗口其实开了 | 拿**按键之前的所有窗口**去比，等于把主窗口也算成新的；改成先记下按键前的集合，只认**新增**的 |
| 同样报"没有新窗口"，这次是真的没开 | 把"模拟点击"放进了条件分支，条件是 `GetForegroundWindow() == hwnd`——**它并不代表该窗口的控件拿到了键盘焦点**，于是条件成立时一次点击都没做，F1 落空 |
| **安静退出，一行输出都没有** | 新加的"起飞前清理同名进程"写了 `taskkill /F /IM python.exe`，而**正在跑这个脚本的也是 python.exe**——它把自己杀了 |

第三条的教训最直接：**清理动作要有"哪些不能清"的清单。** 现在它显式跳过
通用解释器名（`python.exe` / `pwsh.exe` 等）。

**同一个家族第四次**：我第一次拍"产物界面"时抓到一扇 891×938 的旧界面
（来自机器上另一个残留实例），据此差点写下"打包打错了"的结论。修法是让
抓图工具打印并校验**窗口属于哪个可执行文件**——启动的东西与我量的东西必须
是同一个文件，不是就直接失败。

第二条值得记：**代理指标（"它是不是前台窗口"）又一次冒充了"按键真的送到了"。**
判断按键有没有生效，只能看那个窗口有没有出现。

这两个都是**我自己刚写的检查器骗了我自己**，形状完全一样：| 检查 | 我量的 | 应该量的 | 症状 |
|---|---|---|---|
| 提示语会不会被截断 | **Label 自己的宽度**（它跟着文字长） | **容器**分给它的宽度 | "需要 700、分到 700"永远相等 ⇒ 8 行超长提示也被判"没问题" |
| 占位文字会不会被裁 | `dlineinfo` 数行高 | `yview()` 的上界 | 越出视口的行 `dlineinfo` 返回 `None`，**"被裁掉的那几行根本数不到"** |

修完之后的判据：

```python
needed > self.help_strip_text.master.winfo_width() + 2        # 提示语
top, bottom = self.text.yview(); bottom < 0.999               # 占位文字
```

并且补了 `tools/probe_layout_negative.py` 做**阳性/阴性对照**：
两条必然出问题的情形必须被报出来，正常界面必须不报。
**"返回通过"和"根本没检查这一项"在输出里长得一模一样**——
第一版那两个错判就是这么发生的。

## 七、操作与展示逻辑：改了什么，为什么

| 原来 | 现在 | 理由 |
|---|---|---|
| 点「Gen」→ 弹保存框 → 弹一个「成功」对话框，只说路径 | 进度条 + 已生成秒数/字节；完成后状态栏给出两个文件的完整路径，并出现「打开音频」「所在文件夹」 | **成功了要说清生成了什么**。一个模态"成功"对话框挡住的正是用户想看的东西 |
| 生成中只有一条来回跑的进度条 | 不确定态进度条 + 文本读数 + 「取消」 | 上游不预先告诉我们总长度，所以**不给假百分比**；取消后不留半截文件 |
| 322 项语音下拉框，没有搜索 | 筛选框，支持 `en 女` / `zh-CN` / `晓晓` | 322 项里滚是没法用的 |
| 语速/音量/音调没有入口 | 三个输入框 + 实时回显「原声」或「语速 +20%」 | 上游本来就支持，不暴露等于白扔 |
| 编辑区 25 行 `Arial 11`，右键菜单是英文 Copy/Paste/Cut | 跟随主题的等宽不限，`Ctrl+O/S/L`，动态快捷键提示 | —— |
| 无 | 首次运行的提示条、右上角「?」的完整说明、设置窗口（主题/输出目录/代理/提示开关） | 这一版的题目之一就是"新增使用提示" |

> **`F1` 被删掉了**（用户实测反馈）：F1 是很多程序的常用热键，冲突概率高。
> 现在入口只有两个：右上角的「?」按钮与 `Ctrl+H`。删热键之后，**所有提到
> `F1` 的地方都要同步改**——帮助正文、悬停提示、状态栏提示、编辑区下方提示、
> 两份 README、发版说明。这是"改一句话先数副本"那条规矩的又一次应用。

**校验顺序是判据**：任何会导致失败的检查（文本非空、语音已选、参数合法）
都发生在**保存对话框与进度条之前**。用户在任何一步取消，屏幕上都不会
出现进度条——`DevAesthetics` 第 15.3 节那类"空白进度窗"就是这么来的。

## 十三、国际化（中 / English，2026-10-18）

照搬 File Tracker 的 `lang.py` 纪律：**每条用户可见文案都写成
`L("中文", "English")`，两半都在调用点**，不做资源键查找。

- 新建 `lang.py`：`apply("zh"|"en"|"")`、`is_chinese()`、`L()`；
  空值跟随 Windows 用户界面语言（`GetUserDefaultUILanguage`），
  失败时默认英文；`ETTS_LANG=zh|en` 可做测试覆盖。
- `Settings.language` 持久化 `""` / `zh` / `en`；设置窗口新增
  「界面语言 / Language」两个按钮（语言名不翻译）。
- 切换后立即 `apply_language` → 保存 → `retranslate()`：
  - 主界面静态文字、按钮、工具提示、占位符、参数行、状态/计数更新；
  - 设置窗口关闭后按新语言重开（代理值已实时保存，不丢）；
  - 使用提示窗口按新语言重建。
- `params` / `text` / `voices` / `engine` 的用户可见错误与单位也使用 L；
  文件名后缀在英文下变成 `_rate+20%` 这类形式。
- 语言切换时 `retranslate()` 外面套 `platform_win.suspend_redraw(root)`：
  用 Windows `LockWindowUpdate` 把整段更新冻结成一帧，解锁后整棵树
  `RedrawWindow` 一次，避免按钮改宽时旧像素从缝隙里闪出。
- 设置窗口不销毁重建：`_retranslate_settings()` 原地更新标题/说明/按钮，
  否则新 `Toplevel` 的 native 窗口会先以默认尺寸闪一下再变成正式设置窗。
- 测试 `tests/context.py` 固定 `ETTS_LANG=zh`，避免 CI 系统语言导致断言漂移；
  `tests/test_lang.py` 显式验证 zh/en 切换。

**没有翻译的**：语音目录里上游返回的语音名/中文别名、用户输入的文本/路径。
这些是数据，不是界面文案。
